# Claude Code 開発ガイド・プロンプト集 — キャスト管理システム「金魚」

実装はClaude Codeで行う前提。本書は**フェーズ分け／モデル(Opus・Sonnet)の使い分け／そのまま貼れるプロンプト**をまとめる。

---

## 1. モデル使い分けの方針

| 用途 | 推奨モデル | 理由 |
|---|---|---|
| 設計・アーキ決定、給与計算エンジンの設計、セキュリティ/権限設計、難所のレビュー | **Opus** | 仕様の曖昧さを詰め、抜け漏れ・整合性を要する深い推論向き |
| 画面実装、CRUD API、Excel取込パーサ、テスト作成、定型リファクタ | **Sonnet** | 速くコスト効率が良い。仕様が固まった作業を量産 |
| 最終の通し点検・セキュリティ監査・受け入れ確認 | **Opus**（サブエージェントで独立に） | 実装者と別視点で検証 |

**原則：「決める/守る/疑う」はOpus、「作る/量産する」はSonnet。**

### チーム編成（役割）
- **アーキ/レビュアー（Opus）**：設計判断、給与ロジック、権限・セキュリティ、PRレビュー。
- **実装担当（Sonnet）×並列**：フロント、バックエンドCRUD、取込、それぞれ独立タスクで並走。
- **検証担当（Opus、独立サブエージェント）**：給与計算の単体テスト網羅・IDOR/権限の突破テスト・受け入れ確認。
- 並列で走らせる作業は依存が無いものに限る（例：UIガワとDBスキーマは並行可、給与エンジンはスキーマ確定後）。

## 2. 開発フェーズ（マイルストーン）

| Phase | 内容 | 給与情報の必要度 |
|---|---|---|
| 0. 基盤 | リポジトリ・技術選定確定・CI・環境・デザイントークン | 不要 |
| 1. 認証&権限 | ログイン（管理者/キャスト分離）・RBAC・監査ログ土台 | 不要 |
| 2. データ基盤 | DBスキーマ（マルチ店舗）・マスタ・取込バッチ枠 | 不要 |
| 3. Excel取込 | テンプレ定義・パース・検証・洗い替え | フォーマット要 |
| 4. 給与エンジン | 計算ロジック・明細・確定スナップショット | **A群確定が前提** |
| 5. 画面 | 管理ダッシュボード／キャストマイページ・履歴・明細・ランキング・申請 | 一部要 |
| 6. 仕上げ | バックアップ・監視・マニュアル・受け入れ | — |

> **給与のA群（要確認リスト）が未確定の間は Phase 0〜3 と画面のガワまで進め、Phase 4本実装は保留。**

## 3. そのまま貼れるプロンプト集

各プロンプトは「役割・コンテキスト・成果物・制約・完了条件」を含む形にしてある。`docs/` 配下に本資料一式を置き、Claude Codeに読ませる前提。

### 3-0. プロジェクト初期化（Opus）
```
あなたはこのプロジェクトのアーキテクトです。docs/ 配下の要件定義書・設計指針書・データモデル設計・給与計算仕様書・要確認事項リストを読んでください。
タスク：
1. 技術スタックを設計指針の推奨をベースに最終決定し、根拠を ADR（docs/adr/0001-stack.md）に記録。
2. リポジトリ初期構成（フロント/バックエンド/DB/IaC・CI）を作成。
3. デザイントークン（色 #c8243e 他・余白・角丸・タイポ）を1ファイルに定義。
4. CLAUDE.md に開発規約（命名・ディレクトリ・テスト方針・コミット規約）を記述。
制約：マルチ店舗を見据え全テーブルに store_id を持つ前提。秘匿情報は環境変数。外部有料クラウド前提にしない（単一VPS・月額固定の制約）。
完了条件：ビルドが通り、空のヘルスチェックAPIと最小フロントが起動すること。
```

### 3-1. 認証・権限（Opus設計 → Sonnet実装）
```
要件定義書3章・設計指針5章に従い、認証と認可を実装してください。
- 管理者とキャストでログイン経路・権限を分離（RBAC：admin / cast / maintener）。
- パスワードは argon2id、初期PW強制変更、ログイン試行回数制限とロック。
- キャストAPIは常に「認証主体の cast_id」に限定。URL/パラメータで他IDを指定しても他人のデータを返さない（IDOR対策）。
- 重要操作とログイン成否を audit_logs に記録。
完了条件：権限テスト（キャストが他人のデータ・管理API・他店舗データにアクセスできないこと）が自動テストで全て green。
```

### 3-2. DBスキーマ・マスタ（Sonnet、Opusレビュー）
```
docs/04_データモデル設計.md に基づき、マイグレーションを作成してください。
- 全主要テーブルに store_id。pay_rates は有効期間を持つ履歴型。
- payrolls / payroll_items は確定スナップショット用（後のマスタ変更の影響を受けない設計）。
- 本名等の高機微カラムは暗号化方針を反映。
- import_batches を中心に attendances/sales/performance_counts を洗い替え可能（冪等）に。
完了条件：マイグレーションが up/down 両方通り、シードで管理者1・キャスト3・店舗1が作られること。
```

### 3-3. Excel取込（Sonnet）
```
docs に従い Excel 取込機能を実装してください。※実フォーマット未入手のため、まず docs/templates/import_template.xlsx を仮定義し、列マッピングを設定ファイルで差し替え可能にすること。
- アップロード → パース → バリデーション（型・必須・異常値）→ 取込結果プレビュー → 確定/取消。
- 同一バッチ（store_id＋対象期間）の再取込は洗い替え（重複加算を防止）。
- エラー行は行番号と理由を表示。
完了条件：正常Excel取込・不正Excel拒否・二重取込で重複しないこと、をテストで確認。
```

### 3-4. 給与計算エンジン（Opus・最重要） ※A群確定後に着手
```
あなたは給与計算エンジンの設計・実装担当です。docs/03_給与計算仕様書.md を唯一の仕様源とします。
重要：仕様書には★（未確定）が多数あります。★が残る項目はハードコードせず、必ずマスタ（設定）から読む構造にしてください。確定値が無い箇所は仮値をシードに置き、テストで差し替え可能に。
- 計算はサーバー側の単一モジュールに集約。基本給＋歩合＋各種バック−控除＝差引支給。
- 単価は「対象期間時点の pay_rates」を参照。確定時に payrolls/payroll_items へスナップショット保存。
- 端数処理ルールを設定化（切捨/四捨五入・丸めタイミング）。
- 再計算可能・監査可能（内訳を保存）。
完了条件：仕様書の各項目について単体テストを網羅。境界値（0本・大量・前借り超過・端数）を含め green。確定後にマスタを変えても過去明細が不変であることをテストで証明。
```

### 3-5. 画面実装（Sonnet、モック準拠）
```
UIモック（docs/mock 参照）とデザイントークンに従い画面を実装してください。
- キャスト（スマホファースト）：ログイン／マイページ（当月給与・出勤・指名・同伴）／出勤・売上履歴／給与明細／ランキング閲覧／各種申請。下部タブ（ホーム/ランキング/出勤/設定）。
- 管理者（PC）：ダッシュボード（当月売上・本日出勤・本日予約・未承認申請）／キャスト管理／給与明細管理（確定/未確定）／ランキング管理／予約管理／申請承認。
- 金額は大サイズ（44px相当）・本文16px。ブランドカラー #c8243e。
- 全データ取得は権限スコープAPI経由（キャストは本人分のみ）。
完了条件：主要画面がモックと整合し、キャスト画面で他人データが一切表示されないこと。
```

### 3-6. ランキング・申請・予約（Sonnet）
```
- ランキング：指標種別（★pt定義に従う）・対象期間で集計し、公開フラグで表示制御。集計は事前計算してキャッシュ。
- 申請：種別ごとの提出フォーム（スマホ）と管理者の承認/却下、状態遷移、申請者への反映。
- 予約：登録・確認・キャスト紐付け（仕様が浅いため最小実装＋拡張余地を残す）。
完了条件：各機能のCRUDと権限テストが green。
```

### 3-7. 検証・セキュリティ監査（Opus・独立サブエージェント）
```
あなたは実装チームとは独立の検証担当です。以下を敵対的にテストしてください。
1. 給与計算：仕様書の全項目・境界値で期待値と一致するか。端数・前借り精算・確定後不変性。
2. 権限：キャストが他人/他店舗/管理APIにアクセスできないか（IDOR・権限昇格を試行）。
3. 認証：総当たり・ロック・初期PW強制変更が機能するか。
4. 取込：二重取込・不正データで壊れないか。
発見した問題は再現手順付きで issue 化し、修正後に再検証。
完了条件：重大・高リスクの指摘がゼロになること。
```

### 3-8. 仕上げ・引き渡し（Sonnet実装＋Opus確認）
```
- 日次バックアップ（暗号化・世代管理）、死活/エラー監視と通知を設定。
- 管理者向け・キャスト向けの操作マニュアル（docs/manual）を作成。
- 受け入れチェックリスト（要件定義の各IDを満たすか）を作成し全て確認。
完了条件：受け入れチェックリストが全項目クリア。
```

## 4. 運用上の注意（Claude Codeで進める際）
- **docs/ をプロジェクト直下に置き、CLAUDE.md から参照**させると各セッションで仕様が共有される。
- A群（給与）未確定のままPhase 4を走らせない。仮値はシード＋設定で吸収し、確定後に値だけ差し替える。
- 並列実行は「依存の無い独立タスク」に限定（UIガワ＋スキーマは並行可、給与＋取込は順序依存）。
- 各Phase末にOpusの独立レビューを挟む（特に給与・権限）。
